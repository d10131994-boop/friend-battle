# Multiplayer module

The Multiplayer Core contains game-agnostic room, invite, and player contracts.
It does not import the Supabase client and does not depend on a particular
game's UI or game logic.

## Shared Supabase schema

The current shared Multiplayer storage consists of two existing tables in the
`public` schema. Do not create game-specific copies of these tables.

### `public.common_multiplayer_rooms`

| Column | PostgreSQL type | Nullable | Meaning |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Room primary key; generated by the database |
| `game_id` | `text` | no | Game identifier |
| `invite_code` | `text` | no | Unique invitation code; generated by the database |
| `status` | `text` | no | `waiting`, `starting`, `playing`, `finished`, or `cancelled` |
| `max_players` | `integer` | yes | Maximum room capacity; currently nullable |
| `created_at` | `timestamptz` | no | Room creation time |
| `started_at` | `timestamptz` | yes | Game start time |
| `finished_at` | `timestamptz` | yes | Game finish time |

### `public.common_multiplayer_players`

| Column | PostgreSQL type | Nullable | Meaning |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Player-row primary key |
| `room_id` | `uuid` | no | Foreign key to `common_multiplayer_rooms.id`; cascades on room deletion |
| `user_id` | `text` | no | Telegram user ID stored as text |
| `display_name` | `text` | no | Name shown in the room |
| `is_ready` | `boolean` | no | Player readiness; defaults to `false` |
| `is_host` | `boolean` | no | Whether this player is the room host; defaults to `false` |
| `joined_at` | `timestamptz` | no | Time the player joined |

### Existing integrity rules and access

- Room IDs and player-row IDs are primary keys.
- Invitation codes are unique.
- A player can have only one row per room (`room_id, user_id` unique).
- A room can have at most one host (`is_host = true` unique per room).
- Both tables have indexes for room status/creation and player room/user lookup.
- Both tables have Row Level Security enabled.
- No RLS policies currently exist for these tables. The inspected table grants
  include `service_role`; the browser should not access these tables directly.
  Trusted server-side code must validate Telegram `initData` and authorize
  every operation.
- A live check of `pg_publication_tables` confirmed that neither table is
  currently included in a Realtime publication. Do not add them yet: first
  agree on a client-side authorization model and the required RLS policies.
  Enabling Postgres Changes without that access design would not provide a
  usable or adequately specified room subscription contract.

The schema currently has no room creator column separate from the player list:
the host is represented by the player row with `is_host = true`. It also has
no player-left timestamp, room `updated_at`, or room `expires_at` column.
Do not assume these fields exist in queries or response mapping.

## Mapping database rows to Multiplayer Core types

The database uses snake_case; the public TypeScript contract uses camelCase:

| Database | Multiplayer Core |
| --- | --- |
| room `id` | `roomId` |
| room `game_id` | `gameId` |
| room `invite_code` | `inviteCode` |
| room `max_players` | `maxPlayers` |
| player `user_id` | `userId` |
| player `display_name` | `displayName` |
| player `is_ready` | `isReady` |
| player `is_host` | `isHost` |
| player `joined_at` | `joinedAt` |

The server response must assemble a room from one room row and its associated
player rows. Return timestamps as ISO-8601 strings (or `null` where the
TypeScript contract allows it). `maxPlayers` must remain `null` when the
database value is `NULL`. The host must be derived from `is_host`, not from a
non-existent room creator field.

## Database integration

Use `createDatabaseMultiplayerAdapter` to connect the core service adapters to
the public `src/database` API:

```ts
import {
  createDatabaseMultiplayerAdapter,
  createRoomService,
  createInviteService,
  createPlayerService,
} from './multiplayer'

const adapter = createDatabaseMultiplayerAdapter({
  functionName: 'YOUR_SHARED_MULTIPLAYER_EDGE_FUNCTION',
})

export const rooms = createRoomService(adapter)
export const invites = createInviteService(adapter)
export const players = createPlayerService(adapter)
```

The function name is explicit because this repository does not yet contain an
agreed, deployed shared Multiplayer Edge Function. The adapter uses
`database.invokeFunction`; it does not call Supabase directly.

### Edge Function request contract

Each request is sent to the configured function with `initData` and one of
these action payloads:

| Action | Payload fields |
| --- | --- |
| `create_room` | `gameId`, optional `maxPlayers` |
| `join_room` | `inviteCode` |
| `get_room` | `roomId` |
| `set_ready` | `roomId`, `isReady` |

Action names can be overridden in adapter options. The server must validate
Telegram `initData`, derive the acting Telegram user from the validated data,
and enforce authorization. It must not trust a client-supplied user ID.

For all four actions, the current adapter expects the function to return one
normalized `MultiplayerRoom` object:

```ts
{
  roomId: string
  gameId: string
  inviteCode: string
  status: 'waiting' | 'starting' | 'playing' | 'finished' | 'cancelled'
  players: Array<{
    userId: string
    displayName: string
    isReady: boolean
    isHost: boolean
    joinedAt: string | null
  }>
  maxPlayers: number | null
  createdAt: string | null
  startedAt: string | null
  finishedAt: string | null
}
```

The response is a server contract, not a direct PostgreSQL row. The Edge
Function must perform the snake_case-to-camelCase mapping and include the
associated players. Database errors are normalized by the Database module and
propagate through the adapter.

## Realtime

### Current state and prerequisites

The Database module exposes a generic Realtime API, but the shared Multiplayer
tables are not currently in a Realtime publication. Both tables have RLS enabled
without client policies. Therefore this contract is a design specification
only: Multiplayer must not open subscriptions to these tables until the
authorization model, RLS policies, and publication membership have been
reviewed and explicitly approved. Do not change Supabase as part of this
documentation.

The browser must never receive broad access to room/player rows merely to make
Realtime work. The trusted server-side Multiplayer API remains responsible for
validating Telegram `initData` and authorizing room membership. The Realtime
authorization design must ensure that a client can observe only rooms it is
allowed to join.

### Purpose and source of truth

Realtime events are invalidation signals, not authoritative room state.
A Postgres Changes payload must never be cast directly to `MultiplayerRoom`
or merged into the public room model. The trusted `get_room` operation remains
the source of truth and returns the complete normalized room plus its players.

When a relevant event arrives, the client should request a fresh room snapshot
through the existing Multiplayer service. This also handles events arriving
out of order, duplicate notifications, and partial row payloads.

### Proposed subscriptions

Once security and publication prerequisites are approved, a room watcher needs
these subscriptions:

| Table | Events | Filter | Purpose |
| --- | --- | --- | --- |
| `common_multiplayer_rooms` | `UPDATE` | `id=eq.<roomId>` | Room status and lifecycle changes |
| `common_multiplayer_players` | `INSERT`, `UPDATE` | `room_id=eq.<roomId>` | Player joins and readiness/host-field changes |

Use the Database module's existing `realtime.subscribe(table, callback, options)`
API with schema `public`. Keep the two channel handles together as one logical
room watcher and release both with `realtime.unsubscribe(channel)` when the
watcher is stopped.

**Player deletion is an explicit unresolved case.** The current schema
represents leaving by deleting a player row; it has no `left_at` or equivalent
soft-delete field. Postgres Changes DELETE events do not support the same
server-side row filtering guarantees as INSERT/UPDATE, so do not add an
unfiltered DELETE listener as a workaround. Before implementing leave
notifications, agree on a secure signal (for example, an authorized server
broadcast or a schema/event design change). Until then, a deleted player may
not trigger an immediate client refresh through the proposed filtered
subscriptions.

### Snapshot and reconnect lifecycle

1. Create the room watcher and register both subscriptions.
2. Wait until both channels report `SUBSCRIBED`; do not treat the watcher as
   live before that.
3. Fetch `get_room` after subscription setup and publish that complete snapshot.
   This closes the gap between initial room loading and subscription readiness.
4. On each relevant INSERT/UPDATE event, schedule a fresh `get_room` request.
   Coalesce bursts so several row changes cause at most one in-flight refresh
   plus one follow-up refresh if another event arrives during it.
5. On a channel `TIMED_OUT` or `CHANNEL_ERROR`, expose the degraded state to
   the caller. Do not synthesize room state from the failed channel.
6. When the channel returns to `SUBSCRIBED`, fetch a new full snapshot. This
   reconciles changes missed while disconnected.
7. On `CLOSED`, stop treating that channel as active. A deliberate stop should
   unsubscribe both channels and prevent late callbacks from publishing state.

The existing Database Realtime status callback exposes `SUBSCRIBED`,
`TIMED_OUT`, `CLOSED`, and `CHANNEL_ERROR`. A logical room watcher should
report per-channel status (or a derived aggregate status) so callers can
distinguish a fully connected watcher from a partially connected one.

### Ordering, concurrency, and errors

- Treat duplicate events as normal; refreshes must be safe to repeat.
- Do not apply optimistic changes from Realtime payloads to the canonical room.
- Prevent older, slower `get_room` responses from overwriting a newer snapshot.
  Use a monotonically increasing refresh generation or equivalent request
  sequencing in the eventual implementation.
- Keep subscription errors separate from `get_room` errors. Both should be
  observable by the caller.
- Stop/unsubscribe must be idempotent and must prevent callbacks or refresh
  results from updating a stopped watcher.
- Do not add polling, a new Edge Function action, new database columns, or
  game-specific event adapters as part of this contract.

### Out of scope until separately agreed

- Enabling either table in `supabase_realtime`.
- Creating or changing RLS policies, grants, or table schema.
- Defining a new broadcast channel or server-side event publisher.
- Implementing a Multiplayer subscription API or changing game integrations.
- Changing the shared Edge Function request/response contract.

This section records the proposed client contract only. The security design,
player-leave signal, and operational approval are prerequisites for a later
implementation.

## Scope

This module remains independent of game UI and game-specific services.
Existing game integrations are not migrated by this change. This documentation
describes the current database schema; it does not modify Supabase tables,
constraints, RLS policies, grants, Edge Functions, or Storage buckets.
