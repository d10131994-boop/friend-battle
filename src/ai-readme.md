# Инструкции AI по работе с Friend Battle

Этот документ задаёт общие правила работы AI с проектом Friend Battle. Он описывает общие архитектурные принципы, процесс разработки и требования к безопасности. Специфика отдельных модулей должна документироваться в соответствующих документах модулей.

## 1. Проект

Friend Battle — веб-приложение на React, TypeScript и Vite, в том числе предназначенное для запуска внутри Telegram Mini Apps.

Основные технологические компоненты:

- React и TypeScript — клиентское приложение.
- Vite — сборка и локальная разработка.
- Supabase — PostgreSQL, Edge Functions, Storage и Realtime.
- Telegram Mini Apps — пользовательская среда и источник подписанных Telegram initData.

Перед изменениями изучай актуальный код и конфигурацию. Не считай README, комментарии, старые задачи или прежние обсуждения безусловно актуальными: сверяй их с реализацией.

## 2. Общие правила работы

1. Сначала изучи существующую реализацию и зависимости, затем планируй изменения.
2. Реализуй минимальное решение, которое полностью закрывает задачу. Не добавляй абстракции, универсальные слои и заготовки без конкретного сценария использования.
3. Соблюдай существующие архитектурные границы и публичные контракты.
4. Не исправляй несвязанные ошибки и не расширяй scope без согласования.
5. Не маскируй проблемы обходными решениями, ослабляющими безопасность или целостность данных.
6. Разделяй подтверждённые факты, выводы и предположения.
7. Не заявляй о выполненных тестах, сборке, деплое или интеграционной проверке, если они фактически не выполнялись.
8. Если документация расходится с кодом, выясни причину. Не описывай несуществующее поведение и не исправляй документацию на основании догадки.
9. Если обнаружено существенное противоречие в архитектуре или требуется выбор между принципиально разными решениями, остановись на этом решении и обсуди его с пользователем.

## 3. Архитектурные принципы

Проект разделяет ответственность между клиентским приложением, общими модулями, игровыми модулями и серверной инфраструктурой.

- Клиент отвечает за UI, локальное состояние интерфейса, отправку пользовательских действий и отображение серверного состояния.
- Игровой модуль отвечает за правила конкретной игры, игровые состояния, раунды, очки, победителя и игровые результаты.
- Общие модули предоставляют повторно используемую инфраструктуру и контракты.
- Supabase и доверенные серверные компоненты отвечают за проверку прав, критические переходы состояния и достоверность данных.

Не дублируй общую функциональность внутри отдельных игр. Не переноси специфические правила игры в общие модули.

### 3.1. Источник истины

Клиентские данные не являются доверенными только потому, что пришли из приложения. Сервер должен проверять личность, членство, права и допустимость действия.

Критические значения, включая состояние комнаты или матча, очки, победителя и результаты, должны определяться или проверяться на доверенной стороне.

Realtime-события следует рассматривать как уведомления об изменениях, если контракт конкретного модуля явно не определяет иное. Не считай клиентское состояние или payload Broadcast единственным источником истины.

### 3.2. Границы модулей

- Используй публичные API модулей, а не их внутренние реализации.
- Не импортируй внутренности другого модуля ради обхода его контракта.
- Не создавай второй Supabase client.
- Не обращайся к таблицам общей инфраструктуры напрямую из игровых компонентов, если для этого существует публичный API общего модуля.
- Не помещай игровые правила в общую инфраструктуру.

Фактические публичные API, допустимые сценарии и ограничения конкретных модулей определяются их реализацией и документацией соответствующего модуля.

## 4. Работа с Git

### 4.1. Ветки и релизы

Основная последовательность: main → release → task → AI.

Релизная ветка имеет формат:

**friend-battle-{номер-релиза}-release**

Ветка задачи имеет формат:

**friend-battle-{номер-активного-релиза}/{категория}/issue-{номер-задачи}**

Категории задач: common или идентификатор игры, например brain-battle и reaction-rush.

Номер задачи начинается с 001, ведётся отдельно для каждой категории и не используется повторно.

**Важное правило базовой ветки задачи:** имя task branch содержит номер текущего активного релиза, но создаётся от предыдущего релиза — то есть от активного релиза минус один.

Например, для активного релиза friend-battle-02-release:

- task branch: friend-battle-02/common/issue-007;
- базовая ветка: friend-battle-01-release;
- целевая ветка для последующего PR: friend-battle-02-release.

Это сохраняет общую исходную базу задач одного релиза и не подтягивает автоматически изменения других задач, уже влитых в текущий релиз.

Новый релиз создаётся от main. Одновременно ведётся один активный релиз. Новый релиз создаётся после слияния предыдущего релиза в main.

### 4.2. AI-ветки

Основная AI-ветка создаётся от task branch и заканчивается суффиксом -AI.

Дополнительные рабочие AI-ветки создаются от актуальной основной AI-ветки и имеют суффиксы -AI-02, -AI-03 и далее.

AI выполняет работу в AI-ветках, а не непосредственно в task, release или main.

AI самостоятельно выполняет обычные этапы разработки в рамках согласованной задачи: анализ, реализацию, проверки, внутренние PR и слияние дополнительных AI-веток в основную AI-ветку.

Перед итоговым PR необходимо проверить изменения и успешность production build. Если сборка не проходит, не создавай итоговый PR до устранения проблемы или согласованного решения.

Итоговый PR создаётся из основной AI-ветки в task branch. AI не сливает его самостоятельно: пользователь проверяет и принимает результат.

### 4.3. Передача задачи в релиз

После принятия итогового PR в task branch:

1. Проверь, какой релиз сейчас активен.
2. Если активный релиз не изменился, создай PR из task branch в него.
3. Если активный релиз сменился, сначала влей новый релиз в task branch и разреши конфликты в task branch.
4. Проверь совместимость и только после этого создай PR из task branch в новый активный релиз.

Не разрешай конфликты непосредственно в release branch. Не переименовывай task branch при смене релиза. Пользователь проверяет и принимает PR в release branch.

После успешного слияния задачи в релиз удали относящиеся к задаче AI-ветки. Task branch и release branch автоматически не удаляй.

### 4.4. Удаление старых task branches

После слияния релиза в main можно проверять устаревшие task branches.

Проверяются ветки релизов, номер которых на две версии ниже активного релиза или старше. Удалять ветку разрешается только если в ней нет уникальных изменений, отсутствующих в main.

Проверяй реальную историю и содержимое ветки. Не принимай решение только по названию, дате или количеству коммитов. При сомнениях не удаляй ветку и сообщи пользователю.

## 5. Supabase и внешняя инфраструктура

Любые изменения состояния Supabase или другой внешней инфраструктуры требуют предварительного явного согласования пользователя.

Без такого согласования можно изучать схему, метаданные, определения функций, политики, индексы, код, конфигурацию и логи, а также готовить SQL и план изменений.

Перед согласованным изменением:

1. Опиши, что именно будет изменено и зачем.
2. Укажи затрагиваемые объекты и возможные последствия.
3. Подготовь SQL или точный план.
4. Для UPDATE и DELETE сначала проверь область воздействия через SELECT.
5. Выполняй только согласованный объём.
6. После изменения перечитай состояние и проверь результат.

DROP, TRUNCATE, массовый DELETE и другие необратимые действия требуют отдельного явного подтверждения. Не отключай RLS, constraints или triggers для обхода ошибки.

### 5.1. Секреты и клиентская безопасность

- Никогда не помещай service_role, secret keys, bot tokens, signing keys или другие серверные секреты в клиентский код, VITE_* переменные, публичные файлы или Git.
- Клиент может использовать только предназначенный для него публичный Supabase key.
- Не доверяй Telegram ID или другим идентификаторам, переданным клиентом отдельно от проверяемого Telegram initData.
- Серверные операции должны проверять права и допустимость действия.
- Для привилегированных PostgreSQL-функций проверяй SECURITY DEFINER, владельца, search_path и EXECUTE grants.

### 5.2. Миграции

Все изменения структуры БД должны быть оформлены миграциями в предусмотренной проектом структуре supabase/.

Перед созданием миграции изучи существующий механизм и формат миграций проекта. Не придумывай имена, последовательность или механизм применения. Миграции должны соответствовать фактической схеме и ограничиваться текущей задачей.

## 6. Проверки и отчётность

Выбирай проверки, соответствующие затронутому коду. В частности, используй доступные build, lint и тесты.

Различай:

- Проверка исходного кода.
- TypeScript/build.
- Lint.
- Проверка SQL и серверной логики.
- Интеграционная проверка с Supabase.
- Реальное тестирование приложения, в том числе через Telegram и нескольких игроков.

Успешная сборка не доказывает, что интеграция или multiplayer-сценарий работают в реальной среде.

В итоговом отчёте указывай:

- Что изменено и какие файлы затронуты.
- Какие публичные контракты или архитектурные правила изменились.
- Какие проверки фактически выполнены и каков результат.
- Какие проверки не выполнялись и почему.
- Какие действия остаются за пользователем.

Используй точные статусы:

- **Сделано** — изменения внесены.
- **Проверено** — соответствующие проверки фактически пройдены.
- **Проверено частично** — проверена только часть функциональности.
- **Ожидает твоего действия** — требуется действие пользователя.
- **Заблокировано** — продолжение невозможно.

## 7. Документация для AI

Каждый самостоятельный модуль должен иметь собственный ai-readme.md в корне модуля.

Перед работой с модулем AI обязан прочитать его ai-readme.md и сверить инструкции с фактической реализацией.

Если задача меняет архитектуру, публичный API, правила использования, ограничения или поведение модуля, соответствующий ai-readme.md обновляется в рамках той же задачи. Если изменения не влияют на инструкции AI, обновление не требуется.

При изменении общего модуля проверь, затрагивают ли изменения интеграционные правила других модулей. Если затрагивают — обнови соответствующую документацию в том же PR.

Документация должна описывать существующее поведение, реальные API, зависимости, ограничения и запрещённые подходы. Не описывай будущую функциональность как уже реализованную.

Публичные документы не должны содержать секреты, учётные данные или инструкции по эксплуатации уязвимостей. Архитектурные требования безопасности и правила корректного использования защитных механизмов документировать можно.

## 8. Работа с неопределённостью

Не продолжай на основе неподтверждённого предположения, если ошибка может привести к повреждению данных, нарушению безопасности или существенному изменению архитектуры.

Если несколько попыток не дают прогресса, остановись и сообщи:

- Что не получается.
- Что уже проверено.
- Какие гипотезы не подтвердились.
- Что мешает продолжить.
- Какой следующий шаг предлагается.

Не повторяй одинаковые проверки без новой причины и не создавай видимость прогресса.

## 9. Навигация по AI-документации модулей

Корневой документ задаёт общие правила проекта. Перед задачей дополнительно читай документацию тех модулей, чьи API, данные или поведение затрагивает задача.

### Порядок чтения

- **Новая игра:** корневой документ → `src/games/ai-readme.md` → `src/multiplayer/ai-readme.md` → `src/database/ai-readme.md` → документы существующих игр как примеры → создание `ai-readme.md` и README новой игры.
- **Изменение комнат или общей multiplayer-инфраструктуры:** корневой документ → `src/multiplayer/ai-readme.md` → `src/database/ai-readme.md` → AI-документы всех игр, чья интеграция может быть затронута.
- **Изменение Database:** корневой документ → `src/database/ai-readme.md` → документация модулей, использующих изменяемый контракт.
- **Изменение существующей игры:** корневой документ → `ai-readme.md` этой игры → `src/games/ai-readme.md` → `src/multiplayer/ai-readme.md` и `src/database/ai-readme.md` в зависимости от затронутых интеграций.

Документация помогает определить ожидаемые контракты и ограничения, но не заменяет аудит кода. Если документ противоречит реализации или другому актуальному документу, зафиксируй расхождение и выясни его причину до изменения поведения.
